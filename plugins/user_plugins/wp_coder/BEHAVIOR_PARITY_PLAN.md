## 1. Целевое поведение (принципы opencode, а не его код)

1. **Правка — по тексту, а не по номерам строк.** `read` показывает номера
   строк (удобство), но `edit` сопоставляет **текст**. Номера — справочные.
2. **Маленький набор инструментов.** Базовый набор ~15, расширенный — по
   требованию. 55 схем в каждом запросе — это шум и цена.
3. **Завершение — по протоколу, а не по угадыванию.** `finish` + отсутствие
   незакрытых вызовов + явный сигнал; строковые эвристики — только fallback.
4. **Бюджеты — от реального окна модели, а не абсолютные в символах.**
5. **Одинаковые правила для основного цикла и субагентов.**

## 2. Архитектурные решения (принять до кодинга)

| # | Решение | Обоснование |
|---|---|---|
| БД-1 | `read_file` печатает **номера строк** (`\t`-разделитель), но `search_replace` остаётся основным для правки; `edit_file` — для диапазонов, когда номера известны | Номера делают `edit_file` пригодным, но приоритет текстовой правки снимает риск «скопировал номер в query» |
| БД-2 | `looks_like_tool_args_json` ловит и `[…]`, и `{…}`; массив проверяется на ключи инструмента | JSON-массив в чате — это провал отчёта, а не отчёт |
| БД-3 | `kResultBudget`/`kMaxToolOutput`/`session_budget` становятся **относительными** от `model_limits`, когда лимит известен; при неизвестном — прежние значения (обратная совместимость) | Абсолютные константы душат модель с окном 128k; отсутствие лимита не должно ломать текущее поведение |
| БД-4 | Продление бюджета шагов срабатывает и по «правки есть, итога нет», а не только по `todos` | `todowrite` — не все модели его зовут; продление должно зависеть от факта работы |
| БД-5 | Субагент получает то же продление, что основной цикл | Иначе «утыкается даже с субагентами» |
| БД-6 | Профили видимости инструментов: `basic` (~15) и `extended` (все) | 55 схем — это 10k токенов на каждом ходу |
| БД-7 | Явный сигнал завершения (например, `finish` + отсутствие незакрытых вызовов + длина) — основной путь; эвристики остаются fallback | Строковые маркеры хрупки; протокол — нет |

#### И14. P0: фундамент поведения — **✅ завершена 2026-11-21**

- [x] **14.1` `read_file` печатает номера строк; приоритет текстовой правки в промпте.**
  - `read_file` добавляет к каждой строке префикс `%6zu\t` (номер строки, 1-based).
  - Байтовый лимит `read_file_chars_for()` считает и префикс.
  - `search_replace` — основной документированный путь правки; `edit_file`
    (k..query) — когда номера известны из `read_file`. Правки в
    `core/prompts.h` (`kPromptHead`, семейные акценты).
  - Тесты: `read_tool_prints_line_numbers_for_edit_file`,
    `read_tool_line_numbers_respect_offset_and_are_one_based`,
    `read_tool_numbers_count_toward_the_byte_budget`,
    `read_tool_numbers_do_not_break_search_replace`.

- [x] **14.2` Детектор JSON-массивов в `looks_like_tool_args_json`.**
  - `[…]` распознаётся так же, как `{…}`: массив сканируется на ключи
    инструмента (`path`/`content`/`cli`/`query`/…) или на `name`+`arguments`.
  - Массив без ключей инструмента (обычный JSON-отчёт) не трогается.
  - Тесты: `turn_verdict_does_not_close_task_on_a_json_array_of_tool_calls`.

- [x] **14.3` Бюджеты относительно реального окна модели.**
  - `limits::scale_for_context()` = `clamp(context/32768, 1, 4)`;
    `result_budget_for` / `max_tool_output_for` / `read_file_chars_for` /
    `session_budget_for` масштабируют соответствующие бюджеты. Окно 0 → 1
    (обратная совместимость).
  - Применены: `cap_result` (цикл и субагент), `read_file`, `Engine::
    trim_history_if_needed`. Источник окна — `Engine::model_context_limit()`.
  - Тесты: `budgets_scale_from_the_model_window_and_never_shrink`,
    `budgets_never_shrink_below_the_base_constants`.

**Готово, когда:** правка файла перестаёт ломать файл; JSON-массив не
попадает в чат; модель с большим окном не сжимается по 120 000 символов.

## 5. Что осталось (P2, не блокирует паритет)

Эти пункты **не входят** в И14/И15 и не мешают базовому паритету, но
улучшат поведение на слабых/локальных моделях. Заводить отдельной итерацией
(И16+), когда появятся силы:

1. **Полная замена `looks_like_*` на протокол завершения.** Сейчас
   `turn_verdict` (`core/message.cpp`) угадывает «итог/план/handoff» по
   спискам подстрок. Это хрупко by design. Правильный путь — явный сигнал
   (отдельный маркер/`finish`-инструмент), а эвристики оставить только
   fallback'ом для текстового протокола.
2. **Профили `basic`/`extended` в UI.** Настройка `wp_coder.tool_profile`
   читается, но в окне «Сессия» её нет — задать можно только через
   `settings_set`. Добавить переключатель в `ui/coder_window.cpp`.
3. **Масштабирование `kMaxToolOutput` из профиля, а не только из окна.**
   Сейчас `accurate_cloud.json` задаёт `max_tokens: 8192`, и это ограничивает
   ответ, даже если провайдер даёт больше. Сделать `max_tokens` относительным
   от окна модели (как `result_budget_for`), либо задокументировать, что
   `max_tokens` в профиле — это потолок ответа, а не размер окна.
4. **Подсказка про `--ctx-size` для локальной модели.** Хост всегда запускает
   `llama-server` с `--ctx-size` из `settings.ini` (4096). Плагин это не
   переопределяет. В подсказке UI (окно «Сессия») назвать это явно, чтобы
   пользователь понимал, почему локальная модель «не видит» большой контекст.
