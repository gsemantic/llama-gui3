# Changelog

## [0.8.0] - 2026-09-25

Итерация **И3** плана [`AGENT_PARITY_PLAN.md`](AGENT_PARITY_PLAN.md):
«политика команд: blocklist → allowlist». Закрывает дефект **D5** и
последнюю часть вехи M2 «управляемый». До этого исполнение команды
защищал список из девяти подстрок: он ловил ровно то, что в него
вписали, поэтому `rm -rf ~` проходил, а `rm -fr /` — нет, потому что
подстрока ищет `rm -rf /` буквально. Перечислять плохие команды
бесконечно нельзя: список запрещённого всегда длиннее списка
разрешённого. Теперь программа, которой нет в allowlist, не
выполняется.

### Added
- **`core/command_policy.h` + `core/command_policy.cpp` —
  `CommandPolicy { allowed_binaries, arg_rules }` и `ParsedCommand`.**
  - `parse_command_line()` — разбор снятием кавычек **до** проверки.
    Это и есть смысл подхода: `cat x | sh` это две команды, а
    `echo "a | sh"` — одна, где `| sh` часть аргумента. Различия,
    которого строковый поиск не видел в принципе.
  - Обход **рекурсивный**: `|`, `||`, `&&`, `;`, группировка `( … )`,
    подстановки `$( … )`, `${ … }` и backticks. Каждая подкоманда
    проверяется отдельно, вложенность ограничена 8 уровнями — глубже
    отказ, а не пропуск.
  - Валидаторы по бинарнику: `git` (запрет `-c`/`--config-env`
    целиком, `--exec-path`, аргументов с `!`, персистентных
    `core.pager`/`editor`/`alias`/`hookspath` через `git config`),
    `sudo` (`-E`, `--preserve-env`, `-S`, запись в sudoers, `visudo`,
    `tee`), `curl`/`wget` (`--config`, `--upload-file`, `--data*`,
    `--form*`, выгрузка в системный каталог, **allowlist хостов**),
    `rm` (`-r` с абсолютным путём, `~`, `..` и неразрешимым
    значением), `dd`/`mkfs*`/`fdisk*`/`shred` и универсальные обходы
    (`sh`, `env`, `xargs`, `nohup`, `eval`, `su`, `find -exec`),
    код из строки у интерпретаторов (`python3 -c`, `php -r`,
    `node -e`, `perl -e`, `awk 'system(…)'`) и переменные окружения,
    меняющие смысл запуска (`PATH`, `LD_PRELOAD`, `IFS`,
    `GIT_SSH_COMMAND`, …). Запуск **файла** при этом разрешён:
    `python3 script.py` и `php -l index.php` работают.
  - `always_pattern()` (задача 3.5) — безопасный префикс + `*`:
    «всегда разрешить `git status --porcelain`» больше не разрешает
    `git push --force`. Значение флага не путается с подкомандой
    (`git -C /path status` → `git status *`, а не `git -C *`). Для
    нескольких команд или подстановки возвращается `*`, то есть
    «спросить в следующий раз»: выдуманный префикс разрешил бы
    команду, которой пользователь не видел.
  - Сопоставление имён по вариантам: `php8.1` → `php`, `mkfs.ext4` →
    `mkfs`, `python3` → `python`. Одно имя для этого не годится —
    отбрасывание номера версии обрезало `mkfs.ext4` посередине, и
    запрет на `mkfs` переставал срабатывать.
- **Проверка в двух режимах — по источнику бинарника.**
  `check()` (allowlist программ и хостов) вызывает `exec_command`,
  где программу выбирает модель. `check_assembled()` (только
  запреты) вызывает обёртка `shell::run_capture*` для остальных 49
  инструментов, где бинарник выбрал код плагина: `deploy` выполняет
  `./deploy.sh`, `wp_create_site` зовёт `sudo mariadb`, `php_lint`
  запускает `/usr/bin/php8.1`. Для них allowlist был бы не защитой,
  а источником ложных отказов.
- **Проверка стоит в `shell::run_capture` и `run_capture_status`** —
  единственных местах, где собранная плагином команда уходит в
  процесс. Проверка, которую можно забыть, проверкой не является:
  добавление инструмента не должно требовать второго решения «а не
  забыть ли политику». Обёртка `timeout(1)` добавляется **после**
  проверки, иначе allowlist пришлось бы пополнять словом `timeout`.
- **Allowlist сетевых хостов** для `curl`/`wget` в `exec_command`:
  по умолчанию доверен только localhost, `Engine` подкладывает
  `wp_site_url` и `wp_local_url`. Список допустимых, а не
  недопустимых: имя хоста придумать можно любое, поэтому deny-список
  здесь не работал бы никогда.
- **`core/tests` → 259 тестов** (было 234): 22 теста политики команд
  (таблицы разрешённых/запрещённых, рекурсия конвейеров и подстановок,
  always-паттерны, слои правил, allowlist хостов), **таблица из 49
  команд, которые собирает сам плагин**, 2 guard-теста исполнения и
  сквозной тест `exec_command` через настоящий инструмент.
- **Guard-тесты исполнения (задача 3.7).** `no_std_system_in_sources`
  ищет вызов `system(` во всём дереве (мёртвый `wp_deploy_agent`
  выполнял LLM-строку именно так), `all_shell_execution_goes_through_
  the_guarded_wrapper` запрещает прямой `popen`/`execv` мимо
  обёртки. Оба пропускают упоминания в комментариях и строковых
  литералах. Проверены мутацией: с добавленным `std::system` и с
  добавленным `popen` они падают.

### Changed
- **Версия 0.7.0 → 0.8.0** в `plugin.json` (единственный источник
  истины) и в трёх утверждениях `test_manifest_consistency.cpp`.
- **`exec_command` спрашивает разрешение раньше, чем проверяет
  политику** (точка enforcement — по-прежнему `ToolRunner::run`).
  Отказ политики подтверждению пользователем не подлежит: правило
  «bash → allow» не отменяет запрет, иначе политика была бы
  украшением.
- **Кнопка «всегда» для команд предлагает узкий шаблон.**
  Раньше предлагалось само значение, то есть подтверждение
  `git push --force` навсегда разрешало ровно эту строку. Теперь
  `permission_suggested_pattern` для ключей `bash`, `docker`, `cron`,
  `ssh`, `deploy` возвращает `git push *`. Для путей и URL значение
  не сужается: сужать каталог до подкаталога — это другой
  инструмент.
- **`curl` и `wget` убраны из списка подстрок** в
  `security::blocked_commands`. Запрет «любой `curl` подстрокой» —
  ровно тот приём, которым этот список и был заменён. Остальные семь
  строк остались: подстрока ловит и то, что разбор команды не понял.
- **Одно ожидание теста изменено по существу:**
  `permission_suggested_pattern` для `git push --force` возвращает
  `git push *`, а не саму строку. Это и есть задача 3.5 — прежнее
  ожидание кодировало ровно то поведение, которое 3.5 закрывает.

### Fixed
- **`wp_create_site` не создавал сайт: SQL приходил битым.**
  Идентификаторы MySQL обрамлены обратными кавычками, а строка
  заключена в двойные кавычки для shell — а внутри двойных кавычек
  для bash обратная кавычка начинает **подстановку команды**.
  `CREATE DATABASE `wp_site`` выполнял `wp_site` как программу и
  подставлял пустой вывод, то есть к серверу уходило
  `CREATE DATABASE IF NOT EXISTS ;`. Проверено на bash:
  `echo "a `id -u` b"` печатает «a 0 b». Кавычки экранированы.
  Экранирование пароля в этой же строке (дефект **D8**) остаётся
  открытым до И13.3, но теперь пароль со спецсимволом даёт понятный
  отказ политики, а не молча испорченный SQL.
- **Подстановка в команде, собранной плагином, — отказ.** Такой вызов
  всегда признак неэкранированного аргумента (см. выше). В
  произвольной команде подстановка допустима, но её содержимое
  проверяется рекурсивно, а стадия конвейера, целиком состоящая из
  подстановки (`ls | $(which sh)`), отклоняется: выполняется прямой
  вывод другой команды, а вывод политика не разбирает.
- **`/dev/null` и подобные символьные устройства можно писать.**
  Первый вариант политики запрещал любой путь под `/dev`, и это
  сломало бы `2>/dev/null` в каждой второй собираемой команде
  (`systemctl`, health check сайта). Запрещены блочные устройства
  (`/dev/sda`, `/dev/nvme0n1`).
- **`2>&1` больше не превращался в команду `1`.** При разборе цели
  перенаправления амперсанд читался как оператор, команда делилась
  пополам, и `1` становился именем программы — то есть политика
  проверяла не то.

### Known limitations
- Политика не разбирает содержимое скрипта: `./deploy.sh`
  выполняется целиком, команды внутри файла не видны. Барьер —
  ключ разрешения `deploy` и требование, чтобы скрипт лежал в
  проекте.
- Команда на удалённой стороне `ssh` уезжает дословно: `ssh host
  'rm -rf /'` не разбирается. Ключ разрешения `ssh` спрашивает
  пользователя.
- `rm -r *.log` (маска) пропускается: маска раскрывается в текущем
  каталоге, а команда всё равно спрашивает разрешения. Запрет всех
  масок обошёл бы обычную уборку и приучил бы к обходу политики.
- `arg_rules` — слой пользователя: правило может открыть бинарник
  сверх allowlist (`Allow`) или закрыть конкретную команду (`Deny`),
  но **не может отменить кодовый запрет**. Иначе один касательный
  жест в настройках отключал бы защиту. Правила пока не задаются
  настройкой — слой пуст, кроме базового `Ask`.
- Обход политики через доверенный скрипт (тот же пункт, что первый):
  политика проверяет строку, а не то, что лежит по пути.
- `pip install` и `apt-get install` проходят allowlist (нужны для
  работы), но меняют систему — их закрывает разрешение `package`,
  а не политика команд.
- Ключ `doom_loop` объявлен, но вопрос о нём ещё не задаётся: сам
  детектор уже и с правилом-разрешением появляется в И4.11.

## [0.7.0] - 2026-09-25

Итерация **И2** плана [`AGENT_PARITY_PLAN.md`](AGENT_PARITY_PLAN.md):
«система разрешений». До этого плагин спрашивал пользователя ровно в
одном случае — за путь за пределами проекта. Всё остальное (запуск
произвольной команды, деплой, перезапуск службы, `ssh`, создание БД)
разрешалось молча. Теперь решение принимают упорядоченные правила, а
вопрос пользователю задаётся с предлагаемым шаблоном «всегда».

### Added
- **`core/permission.h` + `core/permission.cpp` — правила разрешений.**
  `PermissionAction {Allow, Deny, Ask}`, `Rule {permission, pattern,
  action, comment}` и `Ruleset` — упорядоченный вектор, где **последнее
  совпавшее правило выигрывает**. Порядок правил здесь семантика, а не
  оформление: пользователь дописывает исключение в конец и не обязан
  знать, где стоит умолчание, которое перекрывает.
  `Wildcard::match` — «*» любая последовательность, «?» один символ,
  с откатом по последней `*` (без отката `*.env` не нашёл бы
  `a.b.c.env`). Регулярные выражения сознательно не использованы:
  правила пишет человек, а `*.env` в regex означал бы «что угодно,
  точка, env».
- **`core/permission_engine.h` + `core/permission_engine.cpp` —
  `PermissionEngine`**, член `Engine` (синглтон сессии): ответ «всегда»
  обязан переживать отдельные вызовы инструментов.
  - `evaluate(permission, pattern)`; правил нет — `Ask`. Не описанное
    поведение спрашивает, а не разрешает.
  - `ask(permission, patterns, always_pattern, metadata)` — кондивар
    плюс передача запроса в UI через существующий механизм
    `permission_cv`. Очередь запросов вместо одного: у каждого свой
    `id`, отвечать можно на конкретный. Показывает `AgentState::
    WaitingPermission` и возвращает состояние как было.
  - `reply(id, Once|Always|Reject)`. **Reject каскадирует** на все
    прочие уже висящие запросы (порт `permission/index.ts:109`): одно
    «нет» пользователя не должно превращаться в десять вопросов подряд.
    Каскад бьёт только по уже заданным — следующий вопрос задаётся
    снова, иначе одна кнопка заблокировала бы инструмент до конца сессии.
  - `approve(permission, pattern)` — постоянное разрешение **и
    пересканирование очереди**: подходящие ожидающие разрешаются сами,
    пользователю не нужно нажимать «всегда» второй раз на то же решение.
  - `visible_tools(defs)` — инструмент с catch-all запретом
    (`<ключ> * → deny`) убирается из каталога системного промпта, чтобы
    модель не тратила шаг на заведомо отклонённый вызов (порт
    `disabled()`). Точечный запрет (`read *.env*`) инструмент не прячет.
  - `load_user_rules(json)` — правила пользователя из настройки
    `wp_coder.permission_rules`, дописываются **после** дефолтов и
    перекрывают их. Без этого запреты были бы недостижимы: правила менял
    только `approve()`, а он добавляет только `Allow`.
- **Дефолты уровня агента** (порт `agent/agent.ts:119-140`): `* → allow`
  слабейшим правилом, `read *.env* → ask` (секреты; паттерн с хвостовой
  `*`, потому что `.env.local` встречается чаще `.env`), `bash`, `git`,
  `wp-cli`, `db`, `deploy`, `systemd`, `ssh`, `docker`, `cron`,
  `package`, `rag`, `test`, `doom_loop` → `ask`; `git status/diff/log` →
  `allow` (чтение состояния), `external_directory` → `ask` с whitelist
  доверенных каталогов (data_dir, tmp, навыки).
- **`permission_key` заполнен у всех 50 инструментов** (задача 2.9) —
  по 14 группам вместо 50 отдельных ключей, чтобы «всегда на деплой» не
  разрешало `docker`, а одно правило покрывало всю группу. Словарь ключей
  закрыт тестом: опечатка создала бы ключ, на который нет правил.
- **`PermissionGate` (путь вне проекта) теперь тоже смотрит правила.**
  Whitelist доверенных каталогов иначе был бы мёртвой строкой, а
  «всегда» из гейта — записываться в два места. Ключ
  `external_directory` стал единственным источником истины, список
  `allowed_external_paths` — его сохраняемым отражением.
- **Панель разрешений в UI**: ключ, значение, предлагаемый шаблон
  «всегда», счётчик оставшихся в очереди и три кнопки. Снимок очереди
  берётся до отрисовки и без `st.mtx` (D-6).
- **`core/tests` → 234 теста** (было 179): правила, вилки, дефолты,
  ожидание с ответами из отдельного потока, каскад, пересканирование,
  скрытие инструментов, сквозные проверки через `ToolRunner::run`,
  регрессия на порядок блокировок и параллельное использование.
  `tests/test_support.h` имитирует пользователя, нажавшего «всегда»:
  тесты поведения инструментов не должны проверять разрешения, иначе
  они висели бы на ожидании ответа, которого нет.

### Changed
- **Версия 0.6.0 → 0.7.0** в `plugin.json` (единственный источник
  истины, CMake читает версию оттуда) и в трёх утверждениях
  `test_manifest_consistency.cpp`.
- Точка enforcement разрешений — `ToolRunner::run`, рядом с проверкой
  режима (D-4). Порядок: режим → разрешение → детектор зацикливания.
  Запрещённый режимом инструмент не спрашивает разрешения, а отказ
  попадает в историю вызовов.

### Fixed
- **Кнопка «стоп» работает и на шаге, где агент ждёт разрешения.**
  Прерывание приходит в `PermissionEngine::cancel_all()`, а не через
  чтение `state_` — иначе пришлось бы взять `state_.mtx` поверх
  `mtx_`, то есть дедлок.
- **Новая задача после «стоп» снова задаёт вопросы** (`clear_cancel` в
  `Engine::submit`). Без этого агент получал бы мгновенные отказы на
  всё до конца сессии и не смог бы объяснить пользователю причину.
- **Повторный `load_settings` не размножает правила пользователя** и не
  затирает ответы «всегда»: `apply_agent_defaults` идемпотентна, текст
  правил пользователя запоминается.

### Known limitations
- Правку правил в UI пока нет: запреты задаются настройкой
  `wp_coder.permission_rules`. Панель правил и конфиг-агенты — И8.
- Постоянные разрешения хранятся в правилах сессии, а не в настройках.
  Права на внешние каталоги по-прежнему сохраняются как раньше
  (`wp_coder.allowed_external_paths`).
- Шаблон «всегда» для команд сужается начиная с 0.8.0 (И3.5): в 0.7.0
  он был равен самому значению.
- Ключ `doom_loop` объявлен, но вопрос о нём ещё не задаётся: сам
  детектор уже и с правилом-разрешением появляется в И4.11.

## [0.6.0] - 2026-09-25

Итерация **И1** плана [`AGENT_PARITY_PLAN.md`](AGENT_PARITY_PLAN.md):
«типизированные инструменты». Инструмент стал декларацией (имя,
описание, JSON-схема параметров, флаги), а режимы агента проверяются
в одном месте по этим флагам.

### Added
- **`core/json.h` + `core/json.cpp` — `JsonValue`** (решение D-2).
  Собственный JSON-DOM: `null/bool/int/double/string/array/object`,
  рекурсивный парсер и сериализатор, доступ по пути `get("a.b[0]")`.
  Глубина вложенности ограничена — «забытая» моделью скобка роняет
  воркер-тред рекурсивным разбором. Намеренно не расширение
  `core/json_utils.h`: тот — извлекатель верхнеуровневых полей, схемы
  и произвольные аргументы ему не по силам.
- **`core/tool.h` + `core/tool.cpp` — `ToolDef`, `ToolFlags`,
  `ToolOutput`, `ToolContext`, `ToolHandler2`.** Аргументы инструмента —
  `JsonValue`, а не 8 фиксированных строковых слотов. Добавление
  параметра к инструменту = правка одного файла: объявление в схеме
  рядом с обработчиком; разбор протокола, описание для модели и
  проверка режима подхватывают его сами.
- **Валидация аргументов по схеме** с сообщением в стиле opencode:
  `The <tool> tool was called with invalid arguments: <detail>.
  Please rewrite the input so it satisfies the expected schema.`
  Проверяются обязательность, тип, диапазон и enum. Числа и логика
  принимаются в «приводимом» виде (`"5"` вместо `5`) — локальные модели
  так пишут постоянно, и отклонять такой вызов значит заставлять модель
  тратить шаг впустую. Неизвестные ключи по умолчанию разрешены;

## [0.5.0] - 2026-09-25

Итерация **И0** плана [`AGENT_PARITY_PLAN.md`](AGENT_PARITY_PLAN.md):
«стабилизация и честность». Плагин приведён в состояние, в котором
дальнейший рефакторинг можно делать, не упираясь в ложь документации
и в зависание GUI.

### Fixed
- **P0, зависание всего GUI.** `AgentLoop::run` брал нерекурсивный
  `state_.mtx` вокруг блока «посчитать размер сессии», а внутри вызывал
  `SessionStore::trim()`, который берёт тот же мьютекс. При превышении
  `session_budget` (60 КБ ≈ 12 шагов) воркер-тред вставал намертво,
  а UI — зависал, читая то же состояние под тем же мьютексом.
  Добавлен `SessionStore::trim_if_needed()` — единственная безопасная
  точка входа, мьютекс берётся ровно один раз внутри
  (`core/agent_components.cpp`, `core/agent_components.h`).
- **`exec_command` был невидим для модели.** Инструмент зарегистрирован,
  но не описан ни в одном промпте — то есть модель о нём не знала и
  никогда его не вызывала. Добавлен в таблицу инструментов
  `core/prompts.h` вместе с правилом «крайняя мера».
- **`exec_command` обходил контроль путей.** Единственный инструмент,
  исполнявший произвольный код, был единственным без `PermissionGate`:
  команда, читающая `/etc/shadow` или трогающая `/var/www`, выполнялась
  молча. Добавлена проверка `first_external_path()` + `guard_permission()`.
- **29 инструментов из 50 были невидимы для модели.** Инструменты модулей
  (WordPress / Python / DevOps) описывались только в промпте модуля,
  который инжектился лишь при совпадении `active_module`. На чистой
  установке настройка пуста — модель не знала о `wp_cli`, `docker_build`,
  `pip_install` и остальных. Добавлен каталог инструментов в системный
  промпт, строится из самого реестра (`ToolsRegistry::build_tool_catalogue`),
  поэтому разойтись с кодом не может.
- **Агент оставался без навыков.** `SkillsManager::load()` очищал
  `active_` и не заполнял его, а `set_module()` вызывался только при
  непустой настройке. Результат: `build_skills_prompt()` возвращал `""`,
  и модель не знала, что инструмент `skill_detail` вообще существует.
  Добавлен `refresh_active()` с разумным дефолтом;
  `build_skills_prompt()` больше никогда не возвращает пустую строку.
- **Навыки из `.md` были невызываемыми.** Имя бралось из строки
  заголовка целиком, поэтому `# wp_setup — настройка окружения` давало
  имя `"wp_setup — настройка окружения"`, а `skill_detail` делает точное
  сравнение. Теперь имя — имя файла без расширения (единственная форма,
  которую модель передаст безошибочно), заголовок уходит в описание.
- **Resume сессии молча терял данные.** `load_session` искал `{"role"` и
  брал содержимое до ПЕРВОГО `}` — а `}` есть на каждой второй строке
  кода (`function f() {}`). Написан полноценный разбор со строковыми
  литералами и escape-последовательностями
  (`json::parse_message_array`), битый файл обнаруживается и удаляется.
- **Выход из корня проекта через двоеточие.** `project_resolve()` считал
  абсолютным ЛЮБОЙ путь с `:` на второй позиции (`rel.find(":") == 1`),
  поэтому `a:b/c` уходил наружу мимо `is_path_outside` и
  `PermissionGate`. Теперь диском считается только буква + `:` + разделитель.
- **`save_session` мог оставить обрезанный файл.** Запись идёт во временный
  файл с последующим переименованием.

### Changed
- Версия плагина в одном месте: `plugin.json` — источник истины, CMake
  извлекает её в `WP_CODER_VERSION` для `ll_plugin_info()`. Раньше версия
