# Быстрый и экономный старт сессии

Короткая точка входа. Две команды дают состояние, одна — следующую задачу.
Полные правила — в [`SESSION_START.md`](SESSION_START.md); здесь только то,
что нужно, чтобы начать, и грабли, на которые ушла прошлая сессия.

Ничего изменяемого здесь нет намеренно: номер коммита, число проверок и номер
итерации протухают быстрее, чем файл прочтут. Всё это — команды ниже.

## 1. Состояние

```sh
git -C /home/Alex/projects/llama-b7472-bin-ubuntu-x64/llama-gui log --oneline -1
cd /home/Alex/projects/llama-b7472-bin-ubuntu-x64/llama-gui/build/wp_coder_build \
  && cmake . && make wp_coder_tests -j$(nproc) && ./tests/wp_coder_tests
```

Число проверок сверяется **командой, а не памятью**: расхождение означает, что
что-то изменилось, — разбираться надо, а не подгонять ожидание.

## 2. Первая открытая задача

```sh
cd /home/Alex/projects/llama-b7472-bin-ubuntu-x64/llama-gui/plugins/user_plugins/wp_coder
awk '/^#### /{it=$2} /^- \[ \]/{print it" — "$0; exit}' AGENT_PARITY_PLAN.md
grep -n "<номер задачи>" AGENT_PARITY_PLAN.md | head -3
```

## 3. Что читать, а что — нет

| Читать | Не читать |
|---|---|
| `SESSION_START.md` — правила, действуют в любой задаче | `AGENT_PARITY_PLAN.md` целиком (800 КБ) |
| §4 плана — **только строка нужной задачи**: `sed -n '<N>p' AGENT_PARITY_PLAN.md \| cut -c1-700` | `CHANGELOG.md`, `DEVELOPMENT_PLAN.md` без нужды |
| таблица отклонений — по строке задачи: `grep -n "^| 1[89][0-9] " AGENT_PARITY_PLAN.md` | чужие незакоммиченные правки |

Журнал §4 упорядочен от новых к старым, поэтому `awk … \| head -5` даёт
**последние** закрытые задачи, а не первые.

## 4. Грабли, за которые уже заплачено

1. **«Механизм есть» ≠ «механизм работает».** Прежде чем опереться на
   возможность — найди её **вызывающего**, а не объявление. Реестр сочетаний
   хоста, `LlmClient`, `executeShortcut` — все три выглядели готовыми и были
   мертвы. Ошибка этого класса стоит целой задачи, закрытой внешне.
2. **Проверка, которую нельзя заставить упасть, не является проверкой.**
   Новые проверки и guard-тесты — обязательный мутационный прогон (правило 13
   в `SESSION_START.md`): база зелёная **до** первой мутации, положительный
   контроль обязан упасть, вердикт по коду возврата, имя павшей — разбором
   вывода. Прогон, который не может **назвать** павшую проверку, ничего не
   доказывает; выжившие мутации разбираются руками и пишутся в журнал §4.
3. **Контрольная пересборка с другой конфигурацией ловит то, что `-O0`
   скрывает.** Правило 3 существует не «для перестраховки»: висячая ссылка,
   пойманная в `-O2` с `std::bad_alloc`, на `-O0` проходила зелёной.
4. **Эталон снимается с живого выхода и только после сверки с источником.**
   Выдуманный golden проверяет автора, а не программу, и падает ровно на
   правильном поведении.
5. **Падение по другой причине читается как подтверждение дефекта.** «Агент не
   начал ход» выглядит как «агент завис»; уводит разбор не туда. Проверяй,
   что агент вообще работал, прежде чем судить о его поведении.
6. **Проверка, зелёная на любом коде, опаснее сломанной.** У собственной
   проверки должно быть видно, что именно она нашла: непустой перечень,
   ожидаемое число блоков, положительный контроль на материале в памяти.

## 5. Локи (нарушение вешает GUI)

- `state_.mtx` — нерекурсивный `std::mutex`, общий для всех методов
  `SessionStore` и общий с UI-потоком. **Из кода, который уже держит лок,
  метод `SessionStore`/`Engine` не звать.**
- Под ImGui лок не держать (D1/D6): снимок под локом → отпуск → отрисовка.
- Сначала чужой механизм (`PermissionEngine`, файловый семафор), потом
  `state_.mtx`; порядок блокировок не менять.
- `push_event_` — только после отпускания лока.

## 6. Работа и git

- Одна задача за раз: `cmake .` → сборка → тесты → следующая.
- После правок `CMakeLists.txt` в `build/wp_coder_build` обязателен
  `cmake .`, иначе тесты соберутся со старыми compile definitions.
- Правки `core/*.cpp` и любые guard-тесты — с мутационным прогоном.
- Коммит — на границе задачи; **push после КАЖДОГО коммита**, а не в конце
  итерации.
- Не трогать и не коммитить чужое: корневой `CMakeLists.txt`,
  `profiles/glm 4.7-flash.json`, артефакты сборки в `tests/` и
  `CTestTestfile.cmake`.

## 7. Чего не делать

- Не переоткрывать закрытые решения: причины записаны в §4 и в таблице
  отклонений. Спорить заново — не работа.
- Не заводить новые библиотеки и не расширять зависимости (C++17 и текущий
  набор).
- Не выдумывать номера версий и итераций: они меняются каждый день.
- Не чинить чужой модуль, «падающий» из-за устаревшей сборки: сначала
  `cmake .` и свежая сборка.
