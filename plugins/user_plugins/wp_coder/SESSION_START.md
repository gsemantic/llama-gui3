# Напоминалка для новой сессии

Файл — не отчёт о сделанном, а **правило работы в этом репозитории**.
Поэтому здесь нет ни номера коммита, ни числа тестов, ни номера итерации:
всё это меняется каждый день, а файл перечитывают спустя недели. Всё
изменяемое лежит в [`AGENT_PARITY_PLAN.md`](AGENT_PARITY_PLAN.md) §4
(сводная таблица и журнал) — там и ищи, что сделано и что следующее.
Правило: **этот файл не содержит изменяемых данных**, и тест
`session_start_file_has_no_volatile_data` падает, если появится.

## С чего начать

1. `git log --oneline -1` — где мы находимся.
2. Открыть `AGENT_PARITY_PLAN.md`: §4 (сводная таблица и последние строки
   журнала) и первую итерацию в §3, где остались маркеры `[ ]`. Это и
   есть работа: её номер здесь не записан намеренно.
3. Собрать и прогнать тесты (команды ниже). Число тестов узнай сам, из
   вывода: оно тоже изменяемое.
4. Начать с первой задачи этой итерации. Не с проектирования и не с
   «а посмотрим»: план уже содержит все решения, которые нужно принять.

Если задача не названа — начинай с первой незакрытой. Если перед тобой
другая задача (обсудить, починить, исследовать) — слово «начни» в
сообщении необязательно: правила этого файла действуют в любом случае.

Состояние проверяется двумя командами, а не чтением простыни:

```sh
git -C /home/Alex/projects/llama-b7472-bin-ubuntu-x64/llama-gui log --oneline -1
cd build/wp_coder_build && cmake . && make wp_coder_tests -j$(nproc) && ./tests/wp_coder_tests
cd build && make -j$(nproc) && ctest
```

Следующая итерация — первый заголовок `#### ИN` в §3 плана, в котором
остались маркеры `[ ]`. Не по памяти: после закрытия И3 «делай И4»
протухает сразу же.

## Что закрыто, а что нет

- Авторитетный источник правды — `AGENT_PARITY_PLAN.md`: §0 (дефекты
  D1–D22), §2 (решения D-1..D-8, обязательные ограничения), §3
  (итерации и задачи), §4 (трекинг, вехи, журнал, «Отклонения от плана»).
- Всё, что не перечислено в §3 с маркером `[ ]`, уже сделано. Не
  переоткрывать закрытые итерации и не переизобретать закрытые решения —
  это прямое поручение, а не совет.
- Изменения в `CHANGELOG.md` описывают пользовательское поведение;
  решения с обоснованием лежат в таблице «Отклонения от плана».

## Порядок работы

1. Одна задача итерации → `cmake .` в `build/wp_coder_build` → сборка →
   тесты → следующая задача. Не коммитить в середине итерации.
2. После правок `CMakeLists.txt` в `build/wp_coder_build` обязателен
   `cmake .`, иначе тесты соберутся со старыми compile definitions и
   будут зелёными вхолостую.
3. Граница итерации: обновить §4 плана (маркеры, сводная таблица, волна,
   веха, журнал) → запись в `CHANGELOG.md` → проверить, не изменилось ли
   что-то в этом файле → один коммит.
4. План неточен — сказать и записать в «Отклонения от плана». Молча
   менять зафиксированное архитектурное решение нельзя.

## Критичные ограничения

Нарушение любого из них означает висящий GUI или ложные тесты, то есть
дефект уровня D1/D22, а не мелкую неаккуратность.

1. `state_.mtx` — нерекурсивный `std::mutex`, общий для всех методов
   `SessionStore`. Из кода, который уже держит лок, метод
   `SessionStore`/`PermissionGate` не звать. `push_event_` — только после
   отпускания лока. Прецедент: И0.1.
2. `PermissionEngine` держит свой `mtx_`/`cv_` и никогда не берёт
   `state_.mtx`, удерживая `mtx_`. Прерывание приходит через
   `cancel_all()`, а не чтением состояния под `mtx_`.
3. `wp_coder_core` остаётся статической библиотекой без зависимости от
   хоста — только через `HostCallbacks`. Иначе теряется
   юнит-тестируемость ядра.
4. Реентерабельность: `Engine` — синглтон, состояние протекает между
   тестами. Каждый тест восстанавливает `AgentState`, режим, проект и
   правила разрешений.
5. Инструменты видны модели через `ToolsRegistry::build_tool_catalogue()`.
   Схема инструмента — единственный источник истины и для промпта, и для
   валидации аргументов.
6. Enforcement по режиму (`check_tool_mode_policy`) и по разрешениям
   (`PermissionEngine`) живёт только в `ToolRunner::run`, не внутри
   инструментов.
7. Инструменты с `TF_WRITES_FILES`, разрешённые в режиме «сначала план»,
   обязаны идти через `ToolContext::propose_write`. Список закрыт тестом
   `plan_mode_allows_only_known_proposers_to_write`.
8. Манифест плагина — строго `<имя>.json`, никогда `plugin.json`.
9. Возраст бинарника проверять **до** обвинения кода: «падает в чужом
   модуле» не значит «виноват этот модуль» (D22: «сегфолты»
   `PluginLoader` оказались бинарниками месячной давности). Для тестов
   то же: проверка, которую нельзя заставить упасть, не является
   проверкой — guard-тесты проверяются мутацией.

## Куда смотреть перед правкой

- `core/tool.h` — `ToolDef`, `ToolFlags`, `ToolContext`.
- `core/tool.cpp` — `permission_key_of`, `permission_pattern`,
  `permission_suggested_pattern`.
- `core/agent_components.cpp` — единственная enforcement-точка
  (`ToolRunner::run`).
- `core/command_policy.h` — политика команд; у неё два режима по
  источнику бинарника, см. комментарий в файле.
- `core/shell.h` — единственное место, где команда уходит в процесс.
- `tests/test_support.h` — имитация пользователя, нажавшего «всегда».

Остальное не исследовать без нужды: `README.md` в корне репозитория и
`USAGE.md`/`DEVELOPMENT_PLAN.md` плагина помечены устаревшими, `src/`
содержит только точку входа, `modules/*/module.json` описывают реальные
модули.

## Чего не делать

- Не расширять зависимости и не заводить новые библиотеки: C++17 и
  текущий набор.
- Не возвращать удалённый код (`src/wp_*_agent.*`,
  `wp_coder_orchestrator.*`, `wp_coder_plugin.cpp`): тест
  `no_removed_symbols_in_sources` и `src/README.md` это запрещают.
- Не обходить `shell::run_capture*` собственным `popen`/`system`/
  `execv`: политика команд и таймаут живут там (тест
  `all_shell_execution_goes_through_the_guarded_wrapper`).
- Не чинить чужой модуль, «падающий» из-за устаревшей сборки, и не
  чинить гнилую сборку как таковую — сначала `cmake .` и свежая сборка.
