# Архитектура плагина news_rewriter

Плагин-агент для llama-gui: автономно обходит указанные адреса, забирает новости,
переписывает их через LLM и сохраняет локально. Спроектирован масштабируемым —
новые функции (отправка на сервер, очереди, расписание, другие источники)
добавляются новыми модулями, не затрагивая ядро.

## Цели и не-цели

**Цели**
- Обход списка адресов (RSS/Atom, страницы) по расписанию или вручную.
- Извлечение текста новостей из HTML/фидов.
- Переписывание (рерайт) через LLM-сервер llama-gui (`llm_complete`) или облако.
- Локальное сохранение результатов в структурированном виде.
- UI-окно: источники, статус, запуск обхода, просмотр статей.

**Не-цели (v1)**
- Рассылка по email, индексация в RAG (только закладывается интерфейс `Sink`).
- Ранжирование, дедупликация по смыслу (только по URL/хешу).
- GUI-редактор разметки страниц.

## Ограничения системы плагинов (важно!)

Эти ограничения напрямую формируют архитектуру:

| Ограничение | Следствие |
|---|---|
| Хост-API не даёт сетевых функций | HTTP-клиент и парсеры живут в плагине (своя сборка) |
| `llm_complete` — блокирующий, вызывается из потока | Нельзя вызывать из `ll_plugin_render` (зависание UI); нужен фоновый рабочий поток |
| ImGui-символы резолвятся из exe | Плагин не линкует ImGui, но и не может вызывать его из фонового потока |
| Настройки — JSON-строки через `settings_get/settings_set` | Хранение конфигурации плагина — сериализованный JSON |
| Плагин подключает только `plugin_api.h` и `imgui.h` | Внутренние заголовки приложения недоступны — изоляция полная |

```
│  │(очередь  │   │(HTTP/RSS) │   │(HTML→текст)│  │(LLM-обёртка) │    │

│        │                                 │   Exporter  │◀── Sink   │
│        │                                 │ (стратегия) │   (точка  │
│        │                                 └─────────────┘    роста) │
│        ▼                                                        │
│  ┌──────────────┐   ┌───────────────┐    ┌──────────────┐      │
│  │  Storage     │   │   Config      │    │   Log/State  │      │
│  │ (диск, JSON/ │   │ (settings.ini│    │ (host api    │      │
│  │  Markdown)   │   │  через host) │    │  + свои)     │      │
│  └──────────────┘   └───────────────┘    └──────────────┘      │
│                                                                     │
│  Рабочий поток (worker thread) — fetcher→extractor→rewriter→sink   │
└─────────────────────────────────────────────────────────────────────┘
```

Два уровня:
1. **Main-поток** — только ImGui и диспетчеризация команд. Не блокирующий.
2. **Worker-поток** — цепочка fetch → extract → rewrite → export. Создаётся
   в `ll_plugin_init`, останавливается в `ll_plugin_shutdown`.

## Модули

### Fetcher (загрузка)
- HTTP(S) GET c таймаутами, лимитом размера, редиректами, User-Agent.
- Разбор RSS/Atom (лёгкий XML-парсер — своя реализация или мини-библиотека).
- Прямая загрузка страниц по URL.
- Прокси (`NetworkConfig.proxy`) и кастомные заголовки (`extra_headers`,
  например `Authorization: Bearer <key>`) — ✅ этап 6.2.
- **Точка роста:** очереди для других источников.
- Зависимость: libcurl (статически или dlopen). Решение по линковке — см. «Сборка».

### Extractor (HTML → текст)
- Извлекает заголовок и основной текст новости из HTML.
- План A: конфигурируемые маркеры (`title_marker`/`body_marker`) для конкретных источников.
- План B (✅ этап 6.3): универсальная эвристика «читаемости» по плотности текста
  (density of text) — работает на страницах без маркеров:
  - тело = самый длинный связный набор блоков-«прозы» (words ≥ 2, letters ≥ 15,
    density ≥ 0.5); блоки внутри `nav/header/footer/aside/form` и заголовки
    `h1..h6` исключаются; пустые блоки связку не рвут; fallback — самый длинный блок.
- Убирает рекламу, меню, скрипты, ссылки; нормализует пробелы.

### Rewriter (LLM-обёртка)
- Единственный модуль, который зовёт `g_api->llm_complete`.
- Собирает промпт по шаблону: «перепиши новость своими словами, сохрани факты,
  язык = <config>, тон = <config>».
- Обработка ошибок: сервер недоступен → облако (уже делает хост), таймаут, пустой ответ.
- **Точка роста:** конвейер цепочек промптов, проверка фактов, summary/report.

### Exporter + интерфейс Sink (ключ к масштабируемости)
Абстрактный интерфейс, куда «уходят» готовые статьи. Активный sink выбирается в конфиге.

```cpp
class Sink {
public:
    virtual ~Sink() = default;
    virtual bool write(const Article& article) = 0;   // возврат успеха/ошибки
    virtual const char* name() const = 0;
};
```

Реализации (реестр регистрируется в `ll_plugin_init`):
- `LocalFileSink` (v1) — запись на диск.
- `HttpSink` (✅ этап 6.1) — отправка на сервер: JSON-POST `article_to_json`,
  параметры `url`/`api_key` (→ `Authorization: Bearer`)/`timeout_seconds`/
  `max_retries`/`retry_delay_ms`; успех = HTTP 2xx.
- `EmailSink` / `RagIndexSink` (позже) — рассылка, индексация в RAG.

Плагин регистрирует список доступных Sink-ов; в конфигурации выбирается активный.
Это позволяет добавить «отправку на сервер» **без изменения** fetcher/extractor/rewriter.

### Storage (диск)
- Директория данных: `path_data_dir()`/news_rewriter/ (доступна через host API).
- Структура:
  - `articles/<YYYY-MM-DD>/<slug>.json` — статья в JSON (метаданные + текст).
  - `articles/<YYYY-MM-DD>/<slug>.md` — человекочитаемый рерайт.
  - `state.json` — прогресс обхода, статусы, хеши для дедупликации.
  - `index.json` — маппинг url → локальный файл (для дедупликации).
- Дедупликация по URL-нормализации + SHA-256 содержимого.

### Scheduler
- Периодический обход (интервал из конфигурации) и ручной запуск.
- Очередь задач (url → fetch → … → sink), статусы: pending / fetching / extracting /
  rewriting / exporting / done / error.
- Работает в worker-потоке; состояние видно в UI через `state_get`/логи.

### Config (настройки)
- Через `settings_set/settings_get` (JSON-строка) — ключ `news_rewriter.config`.
- Структура: список источников (url, тип, маркеры `title_marker`/`body_marker`),
  язык/тон рерайта, интервал обхода, активный Sink, сетевые параметры.

### UI (ImGui-окно)
- Таблица источников (добавить/удалить/включить).
- Кнопка «Обойти сейчас», индикатор прогресса.
- Список последних статей + открытие содержимого.
- Команда `news_rewriter_run`, пункт меню «Agents → News Rewriter».

## Модель данных

```json
{
  "id": "sha256(url)",
  "url": "https://example.com/news/42",
  "source": "example.com",
  "fetched_at": "2026-08-08T12:00:00Z",
  "title_original": "Заголовок источника",
  "body_original": "...",
  "title_rewritten": "Заголовок рерайта",
  "body_rewritten": "...",
  "language": "ru",
  "status": "done",
  "error": null
}
```

Статусы статьи: `fetched` → `extracted` → `rewritten` → `exported` (`done`) / `error`.

## Поток выполнения (worker)

```
Scheduler (тик) → Fetcher.load(url) → Extract(source) → Rewriter(промпт)
                 → Sink.write(article) → Storage.save(state)
```
- Каждый шаг отчитывается в общий журнал (`g_api->log`) и в статус статьи.
- Сбой шага → статус `error` + retry-счётчик (не блокирует остальные задачи).
- `llm_complete` вызывается **только** в worker-потоке.

## Сборка

- Директория: `plugins/user_plugins/news_rewriter/` (корневой `plugins/CMakeLists.txt`
  подхватывает `user_plugins`, если тот существует).
- C++17, target `news_rewriter` SHARED, include: `PROJECT_ROOT/include`,
  `external/imgui`, `external/imgui/backends`.
- HTTP: **решение по libcurl** — варианты:
  1. `find_package(CURL)` + статическая линковка в плагин (просто, но тащит зависимость);
  2. `dlopen("libcurl.so")` в рантайме (нужно только `dl`), полная независимость
     от системы сборки плагина — рекомендуемый для v1.
- XML (RSS): собственная мини-реализация или статически встроенный парсер — без
  внешних зависимостей.
- Output: `build/plugins/libnews_rewriter.so` + `plugin.json` рядом (POST_BUILD copy).

## План этапов

| Этап | Содержимое | Критерий готовности |
|---|---|---|
| **0. Каркас** | `plugin_api.h`-обвязка, окно, команда, меню, config, `CMakeLists.txt` | Плагин грузится, окно открывается, нет UI-зависаний |
| **1. Fetcher** | HTTP GET + разбор RSS (без рерайта) | Загрузка фида выводится в журнал/статьи |
| **2. Extractor** | HTML → заголовок+текст по селекторам | Из фида достаются корректные тексты |
| **3. Rewriter** | Worker-поток + `llm_complete` + промпт-шаблон | Статьи переписаны, статусы в UI |
| **4. Exporter/Sink** | Интерфейс `Sink` + `LocalFileSink` + дедупликация | Готовые `.md`/`.json` на диске, повторный обход не дублирует |
| **5. Scheduler** | Периодический обход, состояния, retry | Автономный цикл без участия пользователя |
| **6. Расширения** | `HttpSink` ✅, прокси/авторизация ✅, универсальный extractor ✅ | Подключаются без правок ядра |

Каждый этап завершается рабочим `.so` и commit'ом — приложение при этом
**не пересобирается** (плагин не затрагивает основной проект).

## Тестирование

- Единичные тесты модулей — обычный C++ (fetch/extract с локальным HTTP-сервером).
- Интеграция: загрузка `.so` через `tests/core/test_plugin_loader` приложения.
- Ручной: `cmake --build build` → положить `.so` в `build/plugins/` → запустить GUI.

## Ключевые решения и риски

| Решение | Обоснование / риск |
|---|---|
| Worker-поток + очередь | Обходит блокирующий `llm_complete` и сеть без зависания UI |
| Интерфейс `Sink` с фабрикой | Масштабируемость: новые каналы вывода без правок ядра |
| libcurl через `dlopen` | Изоляция от сборки приложения; риск версий в системе |
| `settings_*` для конфига | Единый механизм persist приложения; JSON-строка |
| Хеширование для дедупликации | Простота; не ловит смысловые дубли (будущая задача) |
