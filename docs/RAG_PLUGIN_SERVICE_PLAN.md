# План: RAG как сервис хоста для плагинов (RAG-SPEC)

> **Статус:** проект, утверждён к реализации (2026-11-23).
> **Область:** хост `llama-gui` (C++), ABI плагинов, `wp_coder` как первый
> потребитель, планируемый парсер сайтов как второй.
> **Не область:** компакшн сессий (отдельная тема), KV-cache префиксов,
> политика слияния сессий. Здесь только инфраструктура, на которую они
> обопрутся.
> **Как обновлять:** правила в §10. Каждая закрытая задача меняет `[ ]` →
> `[x]` и строку в §5 **в том же коммите**, что и код.

---

## 1. Цель и границы

### 1.1. Цель

Сделать RAG **инфраструктурой общего пользования**: любой плагин может
завести собственный изолированный индекс, включать/выключать его
настройками и не иметь возможности ни читать, ни портить чужой индекс.

### 1.2. Критерии успеха (проверяемые)

1. Два плагина индексируют документы в свои скоупы; `search` в скоупе A
   не возвращает документы скоупа B.
2. У `wp_coder` инструмент `rag_index` физически не может перестроить индекс
   другого плагина или приложения.
3. Пользователь выключает RAG для плагина (или глобально) → все
   RAG-вызовы этого плагина возвращают «недоступно», плагин продолжает
   работать без RAG.
4. Плагин, собранный под старый ABI (1.0.0), загружается и работает на
   новом хосте без изменений.
5. Индекс скоупа переживает перезапуск приложения и выгрузку плагина.
6. Индексация большого набора документов ограничена квотой и прерывается
   по «стоп»/дедлайну.
7. `.html`/`.css` индексируются через tree-sitter (AST-чанкинг), а не как
   текст.

### 1.3. Границы (что НЕ делаем в этом плане)

| Не делаем | Почему | Где будет |
|---|---|---|
| Меняем формулу компакшна | `compaction.*` самодостаточен, ломать инварианты нельзя | отдельный план |
| KV-cache префиксов сессий | требует поддержки слотов в хосте | отдельная тема |
| Слияние сессий/ветвей | политика плагина, не хоста | после R5 |
| Облачный RAG / внешние провайдеры эмбеддингов | локальный сервер уже есть | вне рамки |
| Переписывание `RagManager` целиком | достаточно вынести индекс в `RagStore` | R1 |

## 2. Термины

| Термин | Значение |
|---|---|
| **Скоуп (scope)** | Именованное изолированное хранилище: имя, свой индекс, свои чанки, свои квоты, свой путь на диске |
| **Стор (store)** | Реализация одного индекса: `RagStore` (индекс + чанки + метаданные), обёртка над существующей логикой `RagManager` |
| **Реестр (registry)** | `RagRegistry`: создаёт/находит/выгружает сторы по имени скоупа, общий бэкенд эмбеддингов |
| **Бэкенд эмбеддингов** | `EmbeddingGenerator`/`EmbeddingProxy`, общий для всех сторов (модель в памяти одна) |
| **Легаси-скоуп `app`** | Существующий `subsystems.rag_manager`, профиль пользователя; сохраняется для чата и старых плагинов |

## 3. Архитектура

### 3.1. Компоненты

```
┌──────────────────────────────────────────────────────────────────┐
│ Плагины (wp_coder, siteparser, …)                                │
│   вызывают только rag_* через LlamaHostApi (C ABI)               │
└──────────────────────────┬───────────────────────────────────────┘
                           │ plugin_manager.cpp (тонкий слой ABI)
                           ▼
┌──────────────────────────────────────────────────────────────────┐
│ RagRegistry (src/core/rag_registry.{h,cpp})                      │
│  • скоуп → RagStore, мьютекс, LRU выгрузки                      │
│  • проверка прав (has_permission) и enable-флагов               │
│  • квоты, нормализация имён, безопасные пути                    │
│  • один EmbeddingBackend на все сторы                           │
└───────────────┬──────────────────────────────┬───────────────────┘
                │                              │
      ┌─────────▼─────────┐          ┌─────────▼──────────┐
      │ RagStore «app»    │          │ RagStore «plugin:…»│
      │ (текущий профиль) │          │ (изолированный)    │
      │ RagManager+профиль│          │ index + metadata   │
      └───────────────────┘          └────────────────────┘
```

`RagManager` остаётся: из него выделяется всё, что касается одного индекса
(`external_chunks_`, `external_docs_index_`, `save_index`/`load_index`),
и переиспользуется как есть. `RagRegistry` владеет экземплярами.

### 3.2. Модель скоупа

Имя скоупа строит **хост**, не плагин:

```
plugin:<plugin_name>[:<suffix>]
app        — легаси-скоуп (профиль пользователя)
chat       — история чата (зарезервировано)
```

* `<plugin_name>` берётся из `LoadedPlugin::info.name` (уже проверяется на
  непустоту, `plugin_manager.cpp:1880-1886`), санитизируется регуляркой
  `^[a-z][a-z0-9_-]{0,63}$`. Имя, не прошедшее проверку, скоупа не получает:
  `rag_*` возвращают «недоступно», в лог — причина.
* `<suffix>` — необязательный суффикс из настроек плагина (например
  `archive` или `site-example.com`). Двоеточие в суффиксе запрещено (это
  разделитель скоупа), точка и дефис разрешены; проверяется отдельно.
* Полное имя — не путь. Путь выводится только внутри хоста:
  `<data_dir>/rag_scopes/<scope>/index.faiss`, где `<scope>` дополнительно
  кодируется (или проверяется на отсутствие `..`, `/`, `\`).

Конфиг скоупа (host-owned, читается плагином, не пишется):

| Ключ | Тип | По умолчанию | Смысл |
|---|---|---|---|
| `plugin.<name>.rag.enabled` | bool | `true` | Можно ли плагину звать RAG |
| `plugin.<name>.rag.scope_suffix` | string | `""` | Суффикс скоупа |
| `plugin.<name>.rag.roots` | []string | `[]` | Белый список путей для индексации/фильтрации |
| `plugin.<name>.rag.max_docs` | int | `20000` | Предел документов в скоупе |
| `plugin.<name>.rag.max_chunk_bytes` | int | `524288` | Предел одного чанка |
| `plugin.<name>.rag.max_index_bytes` | int64 | `2147483648` | Предел индекса на диске |
| `plugin.<name>.rag.mode` | enum | `hybrid` | `hybrid`/`bm25`/`vector` |

### 3.3. ABI: дополнение, а не замена

**Версию `LLAMA_PLUGIN_API_VERSION` не поднимаем.** Проверка на
`plugin_manager.cpp:1868` строгая (равенство строк), и любой bump выключил
бы все существующие плагины. Новые поля добавляются в конец
`LlamaHostApi`, наличие определяется `api->size >= offsetof(...)` — так уже
сделано для `llm_chat_stream`, `llm_ast_symbols`, `model_info`
(`host_bridge/llm_stream_probe.cpp:18-72`).

```c
/* --- RAG v2: скоупы (append-only) --- */

/* Поиск в скоупе. Возвращает JSON-объект:
   {"ok":true,"chunks":[{content,document_id,chunk_index,file_path,
                         symbol_name,start_line,end_line,score}], "scope":"..."}
   {"ok":false,"error":"...","code":"denied|unavailable|quota|bad_scope"} */
char* (*rag_search_ex)(LlamaPluginHost* host, const char* scope,
                       const char* query, int k, const char* path_filter);

/* Индексация/переиндексация документа в скоупе.
   opts_json: {"max_bytes":N,"max_chunks":N,"deadline_ms":N,
               "reindex":true} (все поля необязательны).
   Возвращает JSON: {"ok":true,"chunks":N,"documents":M,"truncated":bool,
                     "reason":"..."} | {"ok":false,"error":"...","code":"..."} */
char* (*rag_index_document_ex)(LlamaPluginHost* host, const char* scope,
                               const char* path, const char* opts_json);

/* Сведения о скоупе: {"ok":true,"scope":"...","documents":N,"chunks":N,
                      "bytes":N,"created_at":T,"model":"...","ready":bool} */
char* (*rag_scope_info)(LlamaPluginHost* host, const char* scope);

/* Удаление документа/скоупа. Возвращает {"ok":true,...}. */
char* (*rag_scope_remove_document)(LlamaPluginHost* host, const char* scope,
                                   const char* path);
int   (*rag_scope_clear)(LlamaPluginHost* host, const char* scope);

/* Немедленная запись индекса на диск (перед ll_plugin_shutdown). */
int   (*rag_scope_flush)(LlamaPluginHost* host, const char* scope);

/* Отмена идущей индексации по хендлу. Хендл появляется в R4 вместе с
   асинхронной парой rag_index_start/rag_index_wait; до R4 поле
   зарезервировано и возвращает 0. */
void  (*rag_index_cancel)(LlamaPluginHost* host, void* handle);
```

Правила владения памятью — как у существующих: `char*` освобождается
`free_string`; массивы `float` — `free_float_array`.

**Легаси-функции не удаляются.** `rag_search`, `rag_process_document`,
`rag_embedding`, `rag_index_count`, `rag_build_prompt` продолжают работать
в скоупе `app`. Это важно: `wp_coder 0.18.x` и сторонние плагины
компилируются против 1.0.0.

### 3.4. Настройки и права

**Настройки.** `host_settings_get/set` (`plugin_manager.cpp:382-402`) уже
работают с `Settings::custom_settings_` и персистентны (профиль
пользователя, `settings_serialization.cpp:47`). Добавляем:

1. **Namespace-гард в `host_settings_set`:** ключ, начинающийся с
   `plugin.`, разрешён к записи только если это `plugin.<self>.` и **не**
   `.rag.` (host-owned). Иначе `0` и запись в лог. Причина: сейчас плагин
   может записать `plugin.<other>.rag.enabled=true` (`plugin_manager.cpp:391`)
   — это включение RAG за чужого.
2. **Чтение host-owned разрешено** (плагин должен видеть `enabled`, квоты,
   корни).
3. **Флаги верхнего уровня:** `plugin.<name>.rag.enabled` проверяется в
   хосте, а не в плагине.

**Права.** `permissions` из манифеста сейчас парсятся
(`plugin_manager.cpp:1772-1776`) и не применяются. Добавляем
`PluginManager::has_permission(name, perm)` и проверку в `host_rag_*`:

* `rag_search`, `rag_embedding`, `rag_scope_info` → `rag_access`;
* `rag_process_document`, `rag_index_document_ex`, `rag_scope_clear` →
  `rag_write` (новое право; без него только чтение);
* `rag_index_cancel`, `rag_scope_flush` → `rag_access`.

**Ротация доступа (важно, чтобы не сломать сторонние плагины):**

* R1–R2: легаси-функции **предупреждают**, но не отказывают;
* R3: `_ex`-функции отказывают без права; легаси остаётся предупреждением;
* M5: отдельное решение о переходе легаси в отказ (по умолчанию — отказ,
  если за релиз не поступило жалоб).

### 3.5. Данные на диске

```
<data_dir>/rag_scopes/
  plugin_wp_coder/                 # имя скоупа с ':' → '_'
    index.faiss
    index.faiss.metadata.json      # формат версии 3 + scope + owner
    scope.json                     # квоты/флаги на момент создания
  plugin_siteparser_site_example_com/
    ...
```

* Формат метаданных — существующий (`rag_manager_persistence.cpp:88-150`),
  добавляются поля `scope`, `owner_plugin`, `created_at`, `model`.
* Несовместимая модель/размерность → `needs_reindex()` (уже есть), скоуп
  помечается `ready=false`, поиск возвращает `unavailable`, а не
  «пустой результат».
* Удаление плагина не удаляет его скоуп автоматически; есть
  `rag_scope_clear` и (опционально) «очистить при удалении плагина» в UI.

### 3.6. Жизненный цикл

1. `ll_plugin_init` → хост **не** создаёт скоуп (лениво).
2. Первый `rag_*_ex` → `RagRegistry::scope(name)`:
   * проверить `enabled` и права;
   * нормализовать имя;
   * загрузить метаданные или создать пустой стор;
   * если эмбеддинги недоступны → `bm25`-режим (см. 3.7).
3. Индексация/поиск — под мьютексом стора.
4. `rag_scope_flush` / `ll_plugin_shutdown` → `save_index` стора (если
   изменялся) и запись `scope.json`.
5. Выгрузка плагина не выгружает стор из памяти сразу: LRU, минимум 2
   последних использованных; вытесненный стор флашится.

### 3.7. Деградация

| Условие | Поведение |
|---|---|
| Плагин выключен (`enabled=false`) | все `rag_*` → `{"ok":false,"code":"denied"}`, `nullptr` для легаси |
| RAG выключен глобально (`settings.rag().enable_rag=false`) | то же, `code:"disabled"` |
| Нет эмбеддингов (сервер/модель) | `bm25`-режим; `rag_scope_info.ready=false`, `reason:"embeddings unavailable"` |
| Нет FAISS (сборка без `USE_FAISS`) | `rag_search` работает брутфорсом (уже есть fallback), `rag_index_count` = 0 |
| Скоуп повреждён/несовместим | `code:"bad_index"`, плагин получает причину, а не пустой список |
| Квота исчерпана | `code:"quota"`, `rag_index_document_ex` возвращает `truncated=true` |

**Отдельно:** убрать «случайные векторы» в `RagManager::generate_embedding`
(`rag_manager_embedding.cpp:43-62`). Сейчас при недоступной модели поиск
возвращает **правдоподобный мусор** — это худший вид отказа. После R0
генератор возвращает пустой вектор, а вызывающий — внятную ошибку.

## 4. Задачи

Формат: `[ ]` — не начато, `[~]` — в работе, `[x]` — закрыто, `[!]` —
заблокировано. У каждой задачи есть «Готово, когда» и тест.

### R0 — «сначала не врать и не портить» (без ABI)

Цель: убрать дефекты, из-за которых любое расширение RAG опасно.

- [x] **R0.1** Убрать fallback на случайные векторы в
      `RagManager::generate_embedding`; вернуть пустой вектор + причину в
      лог. `rag_search`/`rag_build_prompt` при пустом векторе возвращают
      пустой результат, а не мусор.
      *Готово, когда:* тест `test_rag_embedding_unavailable` даёт пустой
      результат и не «почти совпадение».
      **Сделано (2026-11-24):** `EmbeddingGenerator::load_model()` теперь
      возвращает `false` без пути/URL (было — всегда `true`, из-за чего
      fallback вообще не был виден как отказ); `generate_embedding()`
      возвращает `{}` вместо нулевого вектора (нулевой после нормализации
      даёт косинус 0 — «правдоподобный мусор»); `RagManager::generate_embedding`
      удаляет блок `rand()/RAND_MAX` и логирует отказ один раз;
      `cache_query_response()` не пишет чанки с пустыми эмбеддингами и
      проверяет размерность против `chat_history_index_->d`.
      10 тестов, мутационный прогон: обе мутации пойманы (5 падений и
      2 падения; мутация 2 вскрыла segfault в `faiss::IndexFlat::add`
      на `nullptr` — заодно закрыт проверкой размерности).
- [x] **R0.2** `host_rag_*` учитывают `settings.rag().enable_rag`: если
      выключено — пустой результат/`nullptr` и запись в лог.
      *Готово, когда:* тест с `enable_rag=false` и живым `RagManager`
      возвращает пусто.
      **Сделано (2026-11-24):** одна функция `plugin_rag_allowed()`
      (`src/plugins/plugin_rag_gate.cpp`, объявлена в
      `plugins/plugin_manager.h`) — единственное место решения; все пять
      `host_rag_*` зовут её. `settings == nullptr` → RAG выключен («не
      знаю» = «нет»). 7 тестов в `test_plugin_rag_gate.cpp`, мутационный
      прогон: 2 мутации (`return true` и `settings==nullptr → true`) —
      обе пойманы (2 и 1 падение).
      **Почему отдельный файл, а не plugin_manager.cpp:** в
      plugin_manager.cpp все `host_*` внутри анонимного namespace, и
      функция, объявленная в заголовке, получала внутреннюю линковку
      (`nm`: `(anonymous namespace)::plugin_rag_allowed`) — тест не
      линковался. Это тот же класс, что вынос `ast_symbols` в свой файл.
      **Побочная находка:** `wp_coder`'s `rag_query` на пустой результат
      говорит «проект не проиндексирован»; теперь так же выглядит
      выключенный RAG — сообщение врёт о причине. Вынесено в R5.2.
- [x] **R0.3** Санитизация имени плагина при загрузке: регулярка
      `^[a-z][a-z0-9_-]{0,63}$`; имя не проходит → плагин получает
      предупреждение, скоуп не создаётся.
      *Готово, когда:* тест `test_plugin_name_validation` на пяти
      валидных и пяти невалидных именах.
      **Сделано (2026-11-24):** `plugin_name_is_valid()` и
      `plugin_name_sanitize()` в `include/plugins/plugin_identity.h` +
      `src/plugins/plugin_identity.cpp` (публичные, тестируемые).
      PluginManager санитизирует имя при загрузке, оригинал сохраняется в
      новом поле `PluginInfo::declared_name`. **Ключевое решение:** если
      имя изменилось, к нему добавляется суффикс `-<fnv1a-8hex>` —
      иначе `Плагин` и `Модуль` оба стали бы `plugin` и второй плагин
      молча затёр бы первый (в меню, настройках, RAG-скоупе). Валидное имя

- [x] **R0.4** `.html`, `.htm`, `.css` → `ContentType::Code` в
      `DocumentParser::detect_content_type`; `get_language()` знает
      `html`/`css`. Проверить, что `parse_code_ast` реально вызывает

      *Готово, когда:* `test_document_parser` проверяет `symbol_name` для

## 8. Риски и митигации

| Риск | Вероятность | Последствие | Митигация |
|---|---|---|---|
| Память: N сторов × FAISS | средняя | OOM при 10+ плагинах | LRU + `rag_scope_clear` + квоты |
| N копий модели эмбеддингов | высокая при наивном решении | 117 МБ × N | общий `EmbeddingBackend` (R1.3) |
| Гонки при индексации из фонового потока | высокая | порча индекса | мьютекс стора, порядок `registry → store` (R1.4) |
| Путь-траверсал через имя плагина/суффикс | средняя | запись за пределы `rag_scopes/` | регулярка + `scope_dir` (R0.3, R1.2) |
| Утечка секретов через индекс | средняя | хищение данных | `roots` + фильтр `_secrets`, `*.key`, `*.env` (R1.2/R3) |
| Смена поведения легаси-плагинов | средняя | жалобы | ротация прав, документация, переход в M5 |
| Диск растёт | средняя | заполнение | `max_index_bytes`, `rag_scope_clear`, чистка при удалении плагина |
| `RagManager` не thread-safe | высокая | краш/порча | не звать напрямую; только через стор (R1.4) |
| Сборка без FAISS | низкая | «индекс есть, поиска нет» | явный `code:"unavailable"` и brute-force fallback |

## 10. Правила обновления плана

1. **Одна задача — один коммит.** Вместе с кодом меняются: чекбокс в §4,
   строка в §5, запись в §7 (если решение).
2. **Не перенумеровывать закрытое.** Новые задачи добавляются в конец
   своей итерации; если итерация выросла — открыть следующую (`R6`).
3. **Статусы:** `[ ]` не начато, `[~]` в работе (в §5 — «в работе»), `[x]`
   закрыто, `[!]` заблокировано (в §5 — причина).
4. **Критерий приёмки у задачи обязателен.** Если его нет — задача не
   считается сформулированной.
5. **Тест — часть задачи.** «Работает на живом проекте» не заменяет тест;
   тест обязан падать на мутации (правило проекта).
6. **Отклонение от плана** записывается в §7 с причиной, а не «попутно».
7. **Раз в итерацию** обновлять §5 (сводная) и §6 (вехи).
8. **Перед следующей сессией** читать §4: первая задача с `[ ]` — текущая.

## 11. Связь с компакшном сессий (следующая тема)

Этот план — фундамент для «архива сессий»:

* `plugin:wp_coder:archive` — сюда пишутся свёрнутые головы и выводы
  инструментов с точными локаторами (`session_id`, `call_id`,
  `file:line`);
* `rag_search_ex` — замена «обрезано в 2000 символов» на «можно найти»;
* квоты и персистентность (R4) — обязательное условие, иначе архив не
  переживёт рестарт.

Компакшн остаётся политикой плагина: хост даёт хранилище и поиск, но не
решает, что выбрасывать.
